# WikiPathways linksets

Builds one CyTargetLinker linkset per species from the WikiPathways GMT
release: pathway nodes linked to the genes they contain, with gene ids
expanded to cross-references through BridgeDb.

Published as a single combined Zenodo record,
[10.5281/zenodo.4500957](https://doi.org/10.5281/zenodo.4500957).

## How it runs

`.github/workflows/create-linkset-wikipathways.yml` runs **quarterly, at 03:17
UTC on the 15th of January, April, July and October**, and can also be
dispatched manually. WikiPathways publishes on the 10th of the month, so the
15th leaves a few days of margin.

> GitHub disables scheduled workflows in a repository after 60 days without
> activity, which is shorter than this interval. If a quarterly run does not
> appear, check whether the schedule was disabled in the Actions tab.

Manual dispatch takes four optional inputs:

| Input | Effect |
|---|---|
| `species` | Space-separated codes to build, e.g. `hsa sce`. Default: everything enabled. |
| `version` | A specific WikiPathways release. Default: the current one. |
| `skip_zenodo` | Build and QC only, touch nothing on Zenodo. |
| `force_publish` | Publish even if Zenodo already has this release. |

## The release is resolved, never pinned

`data.wikipathways.org` keeps only a **rolling 12-month window** of monthly
releases, so a hardcoded release eventually 404s. `wp.py` therefore discovers
it, by walking the **dated release directories** listed on
<https://data.wikipathways.org/> (`20260710/`, `20260610/`, …) newest first.

It deliberately does not use `/current/`. That is a moving alias and says
nothing about whether the release behind it is complete, whereas a dated
directory containing a GMT for **every `core` species** is positive evidence
that the release actually shipped. WikiPathways releases on the 10th of the
month, and a release not dated the 10th is flagged in the log.

If the newest directory is incomplete — a release still being published — it is
skipped with a warning and the previous one is used. That is safe because the
workflow refuses to publish a release older than the one already on Zenodo. It
looks at three directories before giving up, since more than a couple of
incomplete releases in a row is a problem to report rather than work around.

Downloads then come from the resolved `/<version>/gmt/` path, so a release
appearing mid-run cannot produce a linkset assembled from two releases.

The resolved release flows into everything that mentions a version: the GMT
URLs, the `version=` line of every generated config, and the Zenodo record
version. **Nothing needs editing when WikiPathways publishes a new release.**

## Adding or removing a species

Everything is driven by [`species.tsv`](species.tsv) — adding a species is one
line there, and nothing else changes.

```
code	wp_token	bridgedb_species	syscodes_out	tier	min_mapped_frac
hsa	Homo_sapiens	Homo sapiens	En,H,L,S	core	0.90
```

- **`wp_token`** is the species as spelled in the GMT filename.
- **`bridgedb_species`** is the key in bridgedb/data `gene.json`. It is stated
  explicitly rather than derived from `wp_token`, because the two sources can
  drift (Ensembl now calls the dog *Canis lupus familiaris*) and because the
  `.bridge` filenames are not derivable from the species name anyway
  (*Equus caballus* is `Qc_`, *Populus trichocarpa* is `Pi_`).
- **`syscodes_out`** are the BridgeDb systems to expand gene ids into. `H`
  (HGNC) is human-only; everything else uses `En,L,S`.
- **`tier`** — `core` means a missing GMT fails the whole run; `extra` means it
  is skipped with a warning; `off` means it is not built.
- **`min_mapped_frac`** is the QC floor for BridgeDb coverage (below).

A species is only worth adding if WikiPathways has real content for it. Five
species are listed but commented out for this reason — pig, horse, poplar,
tomato and maize each have between one and five pathways. `wp.py` also skips
any `extra` species that falls below `MIN_PATHWAYS` (5), so one that shrinks
again will drop out on its own rather than shipping a near-empty linkset.

All GMTs use NCBI Entrez gene ids for every species, including plants, fungi
and insects, so `target_syscode_in` is `L` everywhere and is not a column.

## Configs are generated

There are no committed per-species configs. Each `config/wp_<code>.config` is
generated by `wp.py` from [`wp.config.template`](wp.config.template) on every
run; the whole `config/` directory is gitignored. This is what keeps the
release version from having to be hand-maintained in a dozen places.

The generator asserts that every line of a rendered config is exactly one
`key=value` pair. linksetCreator's `ConfigFileReader` splits on the first `=`
but keeps only lines that split into exactly two parts, silently discarding
anything else — so a value containing `=` would vanish without an error.

## Quality control

Each linkset is validated by `scripts/qc_xgmml.py` before anything is
published. Beyond structural checks it verifies **BridgeDb mapping coverage**:
`--mapped-type gene --min-mapped-frac` fails a linkset unless that fraction of
gene nodes gained more than one identifier. A BridgeDb mapper that fails to
load leaves every node carrying only its input id, which looks structurally
fine but is useless for matching a user's network.

Measured coverage on release 20260710 was 100% for most species, 98.9% for cow
and 95.9% for rat, which is what the 0.90 (core) and 0.80 (extra) floors are
set against.

**Any QC failure fails the whole run and publishes nothing.** A partial publish
would mint a permanent DOI on an incomplete record; a failed run just needs
re-dispatching.

## Publishing

Two gates protect the Zenodo record, both because published versions are
immutable:

1. **Version gate** — if the concept record already publishes this WikiPathways
   release, the run builds and validates but does not publish. Without this a
   quarterly schedule would mint a new DOI every time regardless of whether
   WikiPathways released anything.
2. **Shrink gate** — the run refuses to publish if a file present in the last
   published version is missing from this build, so a transient upstream 404
   cannot silently drop a species from the record.

Publishing needs the `ZENODO_ACCESS_TOKEN` secret.

## Running locally

```bash
pip3 install requests

# All enabled species, current release
python3 wikipathways/wp.py

# One species, and/or a specific release
WP_SPECIES="sce" WP_VERSION=20260510 python3 wikipathways/wp.py

# Build and validate one linkset
scripts/fetch-bridge.sh "$(jq -r '.mappingFiles[]|select(.species=="Saccharomyces cerevisiae")|.downloadURL' gene.json)" bridgedb/sce.bridge
java -jar -Dfile.encoding=UTF-8 linkset-creator-v2.0.jar \
  -c wikipathways/config/wp_sce.config -i input_sce.txt -o wikipathways_sce.xgmml
python3 scripts/qc_xgmml.py --min-nodes 1 --min-edges 1 \
  --mapped-type gene --min-mapped-frac 0.80 wikipathways_sce.xgmml
```

`wp.py` writes `build/version.txt` and `build/manifest.tsv`. The manifest lists
the species that were **actually built** and is what every later workflow step
iterates, so a species skipped during preprocessing can never leave a later
step looking for a file that was never produced.

## Note on BridgeDb downloads

Use `scripts/fetch-bridge.sh`; do not hand-roll a download. Figshare redirects
to a presigned S3 URL that expires in ten seconds, and it answers requests that
look like an interactive browser with `HTTP 202 Accepted` and an empty body.
202 is a success code, so a client that only checks for errors accepts it and
writes a zero-byte file — which is exactly how the previous wget-based download
failed. The script sends no spoofed user-agent and accepts a download only on
an explicit 200 that also passes a zip test.
